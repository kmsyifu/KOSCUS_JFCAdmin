Background
  Every "New DBHelper" (App_Code/DBHelper.vb) reads the registry 3 times, opens an Oracle connection and runs
  "SELECT 1 FROM dual" before any real query. The connection string also has "Connection Lifetime=20", so a
  connection older than 20 seconds is thrown away instead of reused. That makes every extra connection costly,
  and is the likely reason pages are slow only "sometimes". Most speed fixes below remove extra connections and
  repeated queries. DBHelper itself was NOT changed (shared by every page) - see "Not changed" at the end.

1.1 Inventory shows "xx cs, xx ea"

    - CustItem.aspx.vb, both places that set lblPopEditInventory.

    - Width 400px -> 500px (desktop only, Page_Load). Add / Update Item panel margin-left 433px -> 533px so they don't overlap.

1.3 Category dropdown no longer runs the heavy item query a second time
    - Before: on first load and on customer group change, the same big item query ran twice - once only to build the
      Category dropdown, once for the item list.
    - Now: showCustItemSearch resets Category to "All"; showCustItemList runs the item query once and builds the
      Category list from those rows. If an item search text is filled in, it falls back to the old category query.
    - The item grid is now bound from the query result (DataSource) instead of DataSourceID.
    - Categories are listed alphabetically (before: whatever order the database returned).
    - The /*+rule*/ hint was tested and is faster - kept on purpose.
    - Test: Category filter on first load, change customer group, filter by category, item search, save drag-and-drop sort.

3. BRANCH SETTINGS (JFCAdmin/BranchSetting.aspx.vb)
==================================================================================================================================
Bugs
3.1 Save twice deleted a delivery record (Delivery Master detail grid)
    - After Save the grid was not reloaded, so the hidden "old date" still had the date from before the change.
      A second Save treated it as changed again: UpdateDeliveryDate deleted the record already on the new date
      (the one just saved), then updated nothing. The record was gone.
    - Fix: reload the grid after a successful Save. Side effect: the grid goes back to page 1 (same as delete).
3.2 Page stayed in the customer's language after Save with "Send Email"
    - The email loop switches the thread culture to each customer's language and never switched back.
    - Fix: restore the original culture before reloading the grid.
3.3 "Delivery Date To" format check was checking the From box. Fixed.
3.4 Apostrophe (') in a homepage image name caused an Oracle error when opening it.
    - The name was put straight into the SQL. Now passed as a bind variable. The reader is also closed now.
3.5 Mobile style on the detail grid's time / AM-PM / reminder dropdowns was never applied
    (IIf(IsMobile(), lst.CssClass = "...", "") compared instead of assigning). Fixed.

Speed
3.6 Delivery Master detail grid: no DB connection per row (up to 50 per page; lists are built in memory).
3.7 Delivery calendar: loads once even for a month with no deliveries (was up to 42 queries).
3.8 Day-of-week list loaded once and copied to both dropdowns (was the same query twice).
3.9 Branch email read once per Save (was once per row with "Send Email" checked).
3.10 HO admin / KMS support check runs once per page (was in Page_Load, the image detail, and once per branch inside
     the image Save loop).
3.11 Page_Load opens a DB connection only on first load (clicks / tab switches no longer open an unused one).
    - Test: Delivery Master detail - change a date, Save, Save again (date must still be there); once with Send Email;
      paging; Search with bad From / To dates; calendar; open and save a homepage image (try a name with ');
      HO admin saving an image to several branches.

4. ORDER DETAIL (Common/OrderDtl.ascx.vb) - used by Order History
==================================================================================================================================
4.1 Cancel Order could email the wrong text
    - The Cancel Order button did not clear the email subject / body saved by an earlier cancel dialog (for example
      one answered "No", possibly for another order). Confirming then emailed that old text to this order's customer.
    - Fix: clear both before showing the confirm. (This button does not send a cancel email itself today.)
4.2 Update Order crashed on a blank ship date
    - A blank ship date is allowed for branch 05 customers with Anytime Delivery, but the save always parsed it as a
      date. It threw in the middle of the transaction and the changes were lost.
    - Fix: blank saves as no ship date. A typed date is read as MM/dd/yyyy (any other format is read as before).
    - Decision to confirm: blank = no ship date. If it should keep the order's existing date instead, tell Yi.
    - Test: cancel an order (Yes and No); update an order with a ship date and with it blank (branch 05 + Anytime Delivery).

5. ORDER HISTORY (Common/OrderHistory.ascx.vb)
==================================================================================================================================
5.1 Bad order date crashed the page
    - The date format was only checked on Search. Sort, paging, checkbox / company changes and refresh after update
      or delete also load the list, and a bad date reached TO_DATE -> Oracle error.
    - Fix: the check runs every time the list loads; a bad date shows the normal "mm/dd/yyyy format" message.
5.2 "Total N Orders" taken from the grid's own query (dsOrder_Selected) - the whole order query no longer runs a
    second time just to count.
5.3 Removed a customer list query that ran on every list load for JFC admins; its result was only used by the
    CUST / CUSTADMIN cases, which never reach that code.
5.4 DB connection opened only when needed and closed when the page is done (see 7.1).
    - Test: search (check the total count), bad date then change sort, paging, open an order.

7. COMMON / EVERY ADMIN PAGE
==================================================================================================================================
7.1 DB connections left open (connection leak)
    - Balance, Payment Detail (twice on the Balance page), Order History and Item Detail controls each created a
      DB connection for every request, used or not, and never closed it. Under load this can run out of connections.
    - Fix: opened on first use, closed when the control unloads.
      Files: Common/Balance.ascx.vb, Common/PaymentDtl.ascx.vb, Common/OrderHistory.ascx.vb, Common/ShowItemDtl.ascx.vb
7.2 Desktop master (JFCAdmin/JFCAdmin.master.vb): opens a DB connection only on first load (was every click on every
    page) and reads the user's role with one query (was 2-4).
7.3 Mobile master (JFCAdmin/JFCAdmin_Mobile.master.vb): no longer opens a DB connection (it never used one).
    - Test: Branch Settings and Tool menu links show for branch / HO admin and KMS support, hidden for others.
